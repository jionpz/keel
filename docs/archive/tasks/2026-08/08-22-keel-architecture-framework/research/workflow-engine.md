## 1. 需求推导 ✅

**这一节的价值在于：它把"该选什么引擎"从一个品牌偏好问题，变成一个可核对的需求匹配问题。**

从已定稿的架构文档中，逐条抽出对编排层的真实要求：

| # | 需求 | 出处 | 说明 |
|---|---|---|---|
| W1 | 控制平面**确定性可重放** | `04-state-machine.md` §5.3 | 不得在转移判定中用 `now()`、随机数或 LLM |
| W2 | **无限期**等待人工 | `04-state-machine.md` §6 | `human_review_ttl` 刻意不触发自动转移 —— 等待可能持续数天 |
| W3 | **durable timer** | `T-008`（`clarification_ttl`）、`R-009`（wall-clock） | 进程重启后计时器必须还在 |
| W4 | 事件 **at-least-once** 且副作用幂等 | `04-state-machine.md` §5 | — |
| W5 | 崩溃后能恢复"进行到哪了" | 中心不变量 | — |
| W6 | 长时任务（单 Run 可达数十分钟） | Harness 执行特性 | — |
| W7 | 起步规模小 | solo dev / 小团队 | 运维成本必须与规模相称 |

### 1.1 关键观察：这些需求已被数据模型解决了大半

逐条核对本架构**已有的**机制：

| 需求 | 已有机制 | 还需要引擎做什么 |
|---|---|---|
| W1 确定性重放 | 转移表是**显式数据**；facts 只来自 Fact Plane | **无** |
| W4 幂等 | `UNIQUE(idempotency_key)`、`UNIQUE(task_id,kind,key,version)` | **无** |
| W5 崩溃恢复 | 状态在 `task.status` + `event` 表；重启后扫 `status='RUNNING'` 的 run | **无** |
| W2 无限期等待 | `S-HUMAN_REVIEW` 是一个**普通状态**，不是阻塞的调用栈 | **无** |
| W3 durable timer | ❌ 无 | ✅ **需要** |
| W6 长时任务分发 | ❌ 无 | ✅ **需要**（可靠派发 + 重试调度） |

> **结论：真正需要外部引擎提供的只有两样 —— durable timer 与可靠 work queue。**

这个结论不是巧合。它来自一个刻意的设计选择：

> 本架构的状态机是**数据表 + 纯函数转移**，而不是**代码流程**。

而 Temporal / Inngest 这类 durable execution 引擎的核心卖点恰恰是
"**把流程写成普通代码，自动获得持久性**"——
这个卖点在一个已经把流程建模成显式转移表的系统里，**基本用不上**。

两者不是互补，而是**部分重叠**。

### 1.2 Postgres 上补齐那两样的成本

| 能力 | 实现 | 量级 |
|---|---|---|
| durable timer | 一张 `timer(id, fire_at, task_id, payload, fired)` 表 + 轮询循环 | 约 100 行 |
| work queue | 一张 `queue` 表 + `SELECT ... FOR UPDATE SKIP LOCKED` + 重试列 | 约 150 行 |

`SKIP LOCKED` 是 PostgreSQL 9.5 起的标准能力，用于队列是成熟做法。

> ⚠️ 这个估算**只覆盖 v0.1 的单进程场景**。多 worker、优雅关闭、
> 死信队列、限流、可观测埋点会显著增加。诚实的说法是：
> **v0.1 约 250 行；一个生产级队列则是持续投入的组件，不是一次性成本。**

## 2. 候选评估 ⚠️ 未验证

> 以下全部基于训练期知识，**本次会话未能对照官方文档核实**。
> 每一项在被写进 ADR 前都必须查证。

### 2.1 Temporal `未验证`

| 项 | 说明（未验证） |
|---|---|
| 模型 | workflow（确定性，可重放）/ activity（可有副作用）二分 |
| 确定性约束 | workflow 代码不得直接用时钟、随机数、网络 I/O；LLM 调用必须放进 activity |
| 人工介入 | 通过 signal 向运行中的 workflow 投递外部事件 |
| durable timer | 原生支持 |
| 运维 | 需运行 Temporal server 集群（多组件），或用 Temporal Cloud |

**与本架构的匹配度分析**（这部分推理可信，前提是上表为真）：

- ✅ 确定性约束与 W1 **高度一致** —— 本架构本来就要求控制平面确定性
- ⚠️ 但本架构已经**自己**满足了该约束（转移表 + Fact Plane facts），Temporal 的强制机制是**冗余**的
- ❌ workflow-as-code 与显式转移表**重叠**，等于同一个流程被表达两次
- ❌ 运维成本对 W7（solo 起步）不成比例

### 2.2 Inngest `未验证`

| 项 | 说明（未验证） |
|---|---|
| 模型 | 事件驱动 + durable steps（`step.run` / `step.waitForEvent`） |
| 人工介入 | `step.waitForEvent` 等待外部事件 |
| 托管 | 以托管服务为主，自托管方案存在但成熟度未核实 |

⚠️ 托管模式意味着**编排状态出本地**。对一个持有 git 凭据、
处理内部仓库的系统，这是必须先想清楚的数据流向问题（全局红线：网络出口默认拒绝）。

### 2.3 Restate / DBOS / Hatchet `未验证`

均未核实。**不进入 v0.1 候选** —— 不是因为不好，而是因为在完全没查证的情况下引入
一个不熟悉的核心依赖，风险与收益不成比例。

### 2.4 LangGraph 的 checkpoint 模型 `未验证`

它的 checkpointer / `interrupt()` / thread_id 模型在概念上与本架构的
`A-Checkpoint` + `S-HUMAN_REVIEW` 相近，**值得作为设计参照对比**。

但 LangGraph 是**图执行框架**，作用域在单个 agent 流程内部，
而本架构的编排层跨越多个独立进程、多个 Harness、多天的人工等待。
**层级不同，不是同一个位置的候选。**

## 3. 结论 🟡

### 3.1 推荐：v0.1 自研最小状态机驱动

**论证**（依赖 §1，高可信）：

1. 引擎能提供而本架构还缺的，只有 durable timer 与 work queue（§1.1）
2. 这两样在 Postgres 上是**小而确定**的量（§1.2）
3. 引擎的核心卖点 workflow-as-code 与本架构的显式转移表**重叠**，引入它等于同一流程表达两遍
4. 运维成本与 W7 不匹配

**这不是"能力不足所以先凑合"，而是"需求形状不匹配"。**

### 3.2 正面回答：「先自研，后换 Temporal」是路径还是陷阱？

初稿 §4 提出这条迁移路线。答案取决于**一个具体的实现约束**：

> **陷阱**，如果状态转移逻辑写成了命令式的代码流程 ——
> 那么迁移就是把流程重写一遍，"先自研"的投入基本作废。
>
> **可行路径**，如果转移逻辑保持为纯函数：
> ```
> transition(status, control_mode, event, facts) -> (new_status, side_effects[])
> ```
> 那么迁移只是**换掉"谁来调用这个函数、谁来持久化结果"**。
> Temporal 的 workflow 可以是一层薄壳，转移表与 Fact Plane 完全不动。

**因此本研究给实现层加一条硬约束**（应写入 ADR-0003 的 Consequences）：

> 转移函数必须是纯函数，不得内联 I/O、不得读时钟、不得直接调用副作用。
> 副作用只能作为**返回值中的描述**，由外层执行器实施。

满足这条，迁移路径成立；不满足，初稿的设想就是陷阱。
这条约束本身也**独立地**服务于 W1（可重放）—— 它不是为迁移额外付出的成本。

### 3.3 推荐矩阵

| 选项 | 适合 | 选它之后最可能后悔的点 |
|---|---|---|
| **自研最小状态机**（推荐 v0.1） | 单机、小规模、转移表已显式 | 并发 worker 增多后，自建队列的运维细节（死信、限流、优雅关闭）会持续消耗时间 |
| Temporal `未验证` | 多租户、高可靠、团队有运维能力 | 为 workflow-as-code 付了成本，却因已有转移表而用不上；集群运维压过 solo 阶段的收益 |
| Inngest `未验证` | 想省运维、可接受托管 | 编排状态出本地，与凭据/内部仓库的数据流向约束冲突 |
