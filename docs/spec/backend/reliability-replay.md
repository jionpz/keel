# 可靠性故障回放

回放使用临时 Git 仓库、隔离 PostgreSQL 16 和本地 GitHub REST 响应夹具。保留
GitHub provider、控制面和持久事件的实际接线，Harness 使用确定性替身。所有样本
均为隔离回放。生产试运行的证据另见[试运行准入](./trial-readiness.md)。

## 运行回放

使用项目锁定的 Node.js 和 pnpm。将 PostgreSQL 16 客户端加入 `PATH` 后运行：

```sh
git rev-parse HEAD
pnpm run check:isolated pnpm exec vitest run \
  src/e2e/replay.test.ts src/test-support/reliability-metrics.test.ts
pnpm run check:isolated
pnpm run check:isolation
pnpm run check:package
```

在报告中记录提交 SHA、夹具和注入顺序、预期与实际转移、实际动作次数、检查来源、
提交和包的绑定。保留通过、失败和跳过数量。GitHub CI 的记录以 PR 对应提交为准。

## 回放场景

- legacy 已绑定 PR。依次查看旧 SHA 的红灯、当前 SHA 未上报、首轮红灯、第二轮运行中和绿灯。
  数据库应只记录一次重跑认领、当前 SHA 的 `CIPassed` 和绑定 PR 的 `PRMerged`。
  GitHub 替身收到一次 POST，数据库中只有初次 develop。
- legacy 观察过程中注入 429、断连、401、返回旧 SHA 和 PR 换头。
  暂时不可用可重读。没有可信终态时，记录相应等待或错误，返工次数维持为零。
- legacy 在重跑 POST 被服务端接收后断开连接，并发驱动必须共同遵守持久认领。
  第二轮持续失败后进入人工等待。绑定 PR 后续合并时，任务以 `S-DONE` 收口。
- managed 在固定包中声明前端与后端本地检查。回放执行检查 TypeScript 源码与 Python 模块的
  本地命令，持久证据绑定实际执行的检查 ID 和提交。遗漏后端结果时，不能进入 land，
  也不能生成 archive 证据。仓库规则文本中的命令不进入检查执行清单。
- managed 本地证据齐全后，先观察到旧 SHA 上的后端绿灯和当前 SHA 上的前端绿灯。
  当前 SHA 的后端检查出现并失败后，绑定恢复决定只允许重观测一次。重复提交同一决定被拒绝。
  当前 SHA 两项远端检查齐全后才归档，整个过程只执行一次 execute。

工程检查中的跨平台回放使用受控夹具 runner。真正的宿主沙箱由 `check:isolation`
中的项目验证探针单独验证，平台支持范围按该探针的结果记录。

## 指标口径

`summarizeReliability` 用回放取得的事实计算指标。每次调用统计一条工作流，观察窗口
包含起点且排除终点。只纳入窗口内首次认领的任务。尝试、故障和审批按各自持久标识
去重。外部观测冲突和连接故障不进入可信 CI 失败分母。

- **无人工介入交付率**以窗口内首次认领并要求交付的任务为分母。分子是窗口内达到本轨交付条件，且无需人工审批、恢复或外部操作的任务。
- **无进展重跑次数**统计同任务、阶段、提交、包和失败指纹下没有新增可用证据的执行。观测轮询不消耗此计数。
- **每任务 token**对已执行尝试的输入与输出用量求和，包括失败尝试。必要字段缺失时，报告未知总量及已知小计。
- **外部 CI 自动恢复率**以可信 CI 故障为分母。同一 PR 与提交在窗口内转绿，且没有额外 develop、execute 或人工操作，才计入分子。
- **重复人工审批次数**统计针对同一恢复目标、请求修订和失败指纹，在第一笔提交后收到的各笔审批。相同提交标识的重送只计一次。尝试证据未保留时无法从成功决议推算被拒审批。
- **终态一致率**以需要远端对账的本地终态为分母。分子要求该终态符合本轨完成条件，并且与绑定远端事实一致。

可取得分子、分母和未知数的比率独立返回三者。等待和失败保留在交付率分母，未知的
远端一致性也保留在其分母。隔离样本的比率只用于判断夹具中可复现的行为。
