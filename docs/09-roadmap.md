## 1. v0.1 完成判据

初稿 §20 说"先把核心闭环跑起来"，但没说**什么叫跑起来了**。
一个说不清完成标准的目标，会一直"快好了"。

判据（一句可验证的话）：

> **一条真实的用户反馈进入系统后，在无人干预的情况下走完 `S-NEW → S-DONE`，
> 产出一个通过 CI 的 PR；且 `readEvents(task_id, 0)` 能完整重建这个 Task 的全过程。**

三个部分缺一不可：

| 部分 | 为什么必须在判据里 |
|---|---|
| 走完 `S-NEW → S-DONE` | 证明状态机完整，不是"跑到 DEVELOPING 就算通了" |
| **无人干预** | 证明 Policy 与自动派发真的在工作，而不是每步都有人点确认 |
| 事件流能完整重建 | 证明 Fact Plane 真的是事实来源。**没有这条，前两条可能是靠副作用蒙对的** |

### 1.1 判据之外的 v0.1 必须项

以下不在那句话里，但同样是 v0.1 的验收内容（来自 `08-cross-cutting.md`）：

| 来源 | 要求 |
|---|---|
| `S1`–`S3` | Adapter 强制 `CAP-UNTRUSTED_WORKSPACE`；`workspace.untrusted` 无默认值 |
| `O1`–`O4` | 事件流完整、`trace_id` 贯穿、`ContextBuilt` 记录 `source_ref` 与 `dropped` |
| `C1`–`C4` | 成本记录含 `cost_basis` 三态；超预算触发 `C-002` |
| `N1`–`N4` | 每 Task 独立 worktree；乐观锁；单 Task 至多一个 `RUNNING` Run |
| ADR-0003 | **转移函数是纯函数** |

> 最后一条看起来像实现细节，实际是**架构约束**：
> 它同时决定了可重放性与日后迁移到 Temporal 是否可行。

## 2. Non-Goals

明确**不做**的事，及不做的理由。

### 2.1 v0.1 不做

| 项 | 理由 |
|---|---|
| **多项目 / 多租户** | 单 repo 单项目就能验证全部核心机制；租户隔离会污染每一层的接口签名 |
| UI / Dashboard | 事件流 + CLI 足够验证闭环。UI 是消费者，不是被验证的东西 |
| Agent Pool / 并发调度优化 | 并发上限先用保守固定值（`N4`）。优化一个还没跑起来的系统是浪费 |
| 自动合并 PR | 自动开发 + 自动合并 = 无人类检查点。**v0.1 刻意保留最后一道人工闸门** |
| 自动回滚已合并的 PR | 已完成的 Task 是终态、不复活（`04-state-machine.md` §2.3）。回滚开新 Task |
| 多模型路由 / 成本优化 | 模型归 Harness 管（`harness-adapter.md` §4）。Keel 先不插手 |
| Claude Code 与 Human 之外的 Harness | 其接口**未查证**，设计会是虚构（ADR-0005） |
| 完整对话的检索与分析 | 采集归档即可，分析是阶段三 |

### 2.2 Keel 长期也不做

这几条是**定位边界**，不是排期问题：

| 项 | 为什么永远不做 |
|---|---|
| **自己实现 coding agent** | Keel 是编排层之上的 Runtime，不是"又一个 Claude Code"。做了就和自己的 Adapter 竞争 |
| 自己实现模型推理 | 同上，层级不对 |
| 替代 CI | CI 是外部事实源。Keel 消费其结果，不重建它 |
| 通用工作流引擎 | 转移表是**为软件研发流程**定制的。做通用会失去所有领域约束带来的确定性 |

## 3. 与既有工具的边界 · 关闭 G17

初稿从未澄清 Keel 与它周边工具的关系，存在重复造轮子的风险。

| | 负责什么 | 与 Keel 的关系 |
|---|---|---|
| **Keel** | 跨会话、跨角色、跨人机的**流程编排与事实管理** | — |
| **Claude Code / 各 Harness** | 单次会话内的推理、工具调用、代码修改 | Keel 的**执行层**，经 Adapter 接入 |
| **Trellis** | 单个开发者在**单个仓库内**的任务流程与规范注入 | **作用域不同**：Trellis 管一个人一个仓库；Keel 管多任务多角色多天。可共存，见 §3.1 |
| **GitHub Actions / CI** | 代码验证 | Keel 的**外部事实源**，消费其结果（`T-024` / `T-025`） |
| **git** | 版本与隔离 | Keel 的工作区机制（worktree），不自建版本控制 |

### 3.1 Keel 与 Trellis 会重复吗？

**部分会，且必须正视。** 两者都有"任务 / 状态 / 规范注入"的概念。

差别在作用域：

| | Trellis | Keel |
|---|---|---|
| 驱动者 | 人（在 IDE / CLI 里） | 系统（事件驱动） |
| 跨度 | 一次开发会话 | 数天，跨多个角色与会话 |
| 状态 | 文件（`.trellis/tasks/`） | 数据库（事实平面） |
| 人机关系 | 人主导，AI 辅助 | 系统主导，人可接管 |

**判断**：v0.1 不做整合，两者并存。
若日后发现 Keel 的 Developer 阶段实际上就是"跑一次 Trellis 流程"，
那时再考虑把 Trellis 作为一种 Harness 接入 —— 但那是被观察驱动的决定，不是现在该设计的。

> 本仓库自身用 Trellis 开发，这本身就是一个持续的对照实验。

## 4. 阶段推进的触发条件

**不设时间表，只设触发条件。** 时间表会在没准备好的时候逼着推进。

- [ ] ADR-0003、0005 转为 `Accepted`（ADR-0002 已 Accepted）

### 4.2 阶段二内容（按优先级）

| # | 内容 | 为什么是这个顺序 |
|---|---|---|
| 1 | **接入第二个 AI Harness** | "Harness 可替换"在 v0.1 **未被充分证伪**（ADR-0005）。这是最该先验证的主张 |

### 4.3 关于 dogfooding（PRD Q5）

**推荐：阶段二再做，不在 v0.1。**

理由：dogfooding 的价值在于暴露真实痛点，但前提是系统已经稳定到
**失败是信息而不是噪音**。在 v0.1 阶段，任何失败都可能是基础实现问题，
分不清是"流程设计有缺陷"还是"代码还没写完"。

触发条件：阶段二 #1 完成后（即至少两个 AI Harness 可用），
先用 Keel 处理**低风险任务**（文档更新、依赖升级），再逐步放开。

### 4.4 阶段三触发

- [ ] 阶段二完成
- [ ] 出现**明确的规模压力**（并发瓶颈、成本失控、多项目需求）

阶段三内容：Temporal 重估（ADR-0003）、多项目调度、Agent Pool、
分布式追踪后端、成本归因报表、Evaluation。

> 阶段三的每一项都应由**观察到的问题**触发，而不是由"架构应该有这些"触发。
> 初稿把它们列成了一张待办清单，本文把它们改成了一组条件。
